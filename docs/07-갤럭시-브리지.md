# 갤럭시 브리지: Samsung Calendar ⇄ 구글 메인 계정 (0.8.0)

2026-10-17

## 1. 왜 필요한가
- 갤럭시 사용자는 일정을 **Samsung Calendar(삼성 계정)**에 저장합니다. 그래야 갤럭시 폰·탭·북이 삼성 클라우드로 같은 일정을 공유합니다.
- Samsung Calendar는 아이폰으로 가지 않습니다. 아이폰은 삼성 계정을 읽지 못합니다.
- 0.7.0까지의 "Google로 옮기기(원본 삭제)"는 원본을 지우므로 갤럭시 생태계를 깨뜨립니다. 그래서 **원본을 유지한 채 양방향으로 계속 맞추는 브리지**로 바꿉니다.

```
 갤럭시 생태계 (폰·탭·북)           구글 메인 계정 (허브)           애플 생태계
 Samsung Calendar ⇄ [OLO 브리지] ⇄        ●        ⇄ (iOS 기본 기능: CalDAV) ⇄ 아이폰·아이패드·맥
```

## 2. 결정 사항(사용자 승인)
- **담는 곳:** 구글 메인 계정의 기본 캘린더. 추가 로그인이 필요 없습니다.
- **충돌:** 양쪽이 동시에 바뀌면 Samsung 쪽을 남기고 횟수를 알립니다.
- **아이폰:** 구글 메인 계정을 직접 씁니다(iOS 기본 기능). iCloud 브리지는 나중에 넣습니다.

## 3. 동작
| 항목 | 구현 |
|---|---|
| 단위 | "시리즈". 단일 일정, 또는 반복 일정 + 그 예외 회차(변경·취소)를 하나로 봅니다. |
| 같음 판정 | 지문(fingerprint, FNV-64 해시): 제목·장소·메모·종일·시작·끝·시간대·반복 규칙(정규화: `WKST=MO` 제거, 항목 정렬)·제외 날짜·알림 분·예외 회차. 동기화 어댑터가 덧붙이는 관리용 값은 넣지 않습니다. 그래서 브리지가 쓴 내용이 메아리처럼 되돌아와도 아무 일도 일어나지 않습니다. |
| 짝 기록 | (Samsung id, 구글 id, 각 쪽 지문)을 OLO 설정(`bridge.links`)에 저장합니다. |

| 안전 정지 | 한 번에 지워질 시리즈가 max(5, 짝 수의 20%)를 넘으면 삭제를 보류하고 확인을 받습니다. 나머지 반영은 그대로 진행합니다. |

| 되읽기 | 쓴 뒤 양쪽을 다시 읽어, 실제 저장된 지문으로 짝 기록을 갱신합니다. 쓰기가 실패한 짝은 예전 지문을 유지하므로, 다음 번에 다시 시도합니다. |
| 실행 시점 | 앱이 켜져 있을 때: 저장소가 바뀌고 3초 뒤.<br>앱이 꺼져 있을 때: WorkManager<br>· 캘린더 저장소가 바뀌면 깨어나는 1회성 작업(5초 모아서, 최대 60초). 실행 뒤 다시 걸어 둡니다.<br>· 놓친 변경을 메우는 15분 주기 작업 |
| 화면 | 짝지어진 일정은 OLO에서 Samsung 쪽 하나만 보입니다. 변경 회차도 시리즈 id로 함께 숨깁니다.<br>서랍의 Samsung Calendar 줄: "구글 메인과 연결 ›" → 연결 후 "● 구글 메인 연결 · 맞춤 n분 전"<br>연결 화면: 구글 계정 선택, 첫 연결 미리보기(삼성→구글 n · 구글→삼성 n · 짝만 지음 n), 동기화가 꺼진 계정 바로 켜기, 지금 맞추기, 보류된 삭제 진행, 연결 해제(양쪽 일정은 그대로 둠) |

## 4. 한계와 주의
- **브리지 기기는 한 대:** 갤럭시 여러 대에서 브리지를 켜지 마세요. 짝 기록이 기기마다 따로 있습니다. 첫 연결의 "같은 일정 짝짓기"가 중복을 상당 부분 막지만 완전하지 않습니다.
- **삼성 캘린더 앱의 중복:** 삼성 캘린더 앱에서 구글 메인 캘린더 표시를 끄도록 연결 화면에서 안내합니다. 양방향 복제라서 빠지는 일정은 없습니다.
- **Samsung 전용 정보:** 스티커, 음력 반복 등은 Google에 담기지 않습니다. 반대 방향 갱신도 화면에 보이는 값만 덮어씁니다.
- **iOS 쪽 반영 속도:** 아이폰의 "데이터 가져오기" 주기를 따릅니다.
- **실기기 확인이 필요한 부분:** Samsung 계정 캘린더에 예외 회차를 넣는 동작, 삼성 클라우드가 동기화 중에 고치는 값이 지문을 흔드는지 여부. 흔든다면 정규화 항목을 추가합니다.

## 6. 0.8.1: "켜지지 않음" 수정 (실기기 지적)
- **증상:** "꺼짐 → 캘린더 동기화 켜기"를 눌러도 "휴대폰이 허용하지 않아…" 알림만 뜨고 켜지지 않았습니다. 세 계정이 모두 "꺼짐"으로 보이던 것도 같은 원인으로 봅니다.
- **원인(추정):** Android 8부터 앱은 다른 앱(Google)이 만든 계정을, 사용자가 시스템 계정 선택 화면에서 한 번 고르기 전에는 볼 수 없습니다. 그 전까지 OS는 동기화 상태를 오류 없이 "꺼짐"으로 답하고, 켜기 요청도 오류 없이 무시하는 것으로 보입니다. 실기기에서 확인이 필요합니다.
- **수정:**
  - OLO가 볼 수 없는 계정은 "꺼짐"이 아닌 **"확인 필요"**로 표시합니다(`SyncStatus.accountsNeedingAccess`).
  - "허용하고 동기화 켜기"를 누르면 계정 선택 화면(`AccountManager.newChooseAccountIntent`)이 뜹니다. 그 계정을 고르면 OLO가 계정을 볼 수 있게 되고, 바로 동기화를 켭니다.
  - 그래도 휴대폰이 거부하면 전체 동기화 목록이 아닌 **그 계정의 동기화 화면**(`android.settings.ACCOUNT_SYNC_SETTINGS`)을 엽니다.

## 7. 0.8.2: 첫 연결에서 생긴 두 배 중복 수정 (실기기 지적)
- **증상:** 연결 후 Samsung Calendar와 구글 sutest가 각각 일정 1412개가 되었습니다(원래 Samsung 799개). 같은 일정이 두 벌씩 생겼습니다.
- **원인:**
  - "연결 시작"을 누르면 첫 맞춤과 동시에 백그라운드 작업이 등록됐습니다.
  - 이 작업은 캘린더가 바뀌면 바로 깨어납니다. 그래서 첫 맞춤이 쓰는 도중에, 별도의 엔진으로 두 번째 맞춤을 시작했습니다.
  - 잠금 장치가 엔진마다 따로 있어서 서로를 막지 못했습니다. 짝 기록은 맞춤이 끝날 때 한 번만 저장되므로, 두 번째 맞춤은 짝이 없다고 보고 같은 일정을 또 복제했습니다.
- **수정:**
  1. 잠금을 프로세스 전체에서 하나로 바꿨습니다. 화면과 백그라운드의 맞춤이 겹치지 않습니다.
  2. 짝 기록을 25개마다 중간 저장합니다. 맞춤이 도중에 끊겨도 처음부터 다시 복제하지 않습니다.
  3. 백그라운드 작업은 첫 맞춤이 끝난 뒤에 등록합니다.
  4. 계획 단계에서, 이미 짝지어진 일정과 내용이 똑같은 짝 없는 일정은 반대편으로 복제하지 않습니다(`duplicates`로 셉니다).
  5. **중복 정리:** 연결 화면에 "똑같은 일정이 두 벌 있습니다 · 중복 n개 정리"를 표시합니다.
     - 지문이 완전히 같은 일정끼리만 골라, 짝이 있는 쪽 중 가장 오래된(원본) 하나만 남깁니다.
     - 지워진 일정을 가리키던 짝 기록은 먼저 지웁니다. 그래야 반대편 짝까지 따라 지워지지 않습니다.
     - 정리 후 맞춤을 한 번 돌려 다시 짝짓습니다.
- **테스트 추가:** 겹친 맞춤으로 생긴 두 벌 정리, 짝 있는 일정의 쌍둥이를 복제하지 않는지 확인

## 8. 0.8.3: 일정 103개 유실 사고와 재발 방지 (실기기 지적)
- **증상:** 중복 정리 후 양쪽 799개였던 일정이, 약 45분 뒤 양쪽 모두 696개가 되었습니다. 같은 일정 103개가 양쪽에서 함께 사라졌습니다.
- **경로:** 양쪽에서 함께 사라질 수 있는 경로는 브리지의 "삭제 따라가기"뿐입니다.
  - 짝의 한쪽이 보이지 않으면, 브리지는 "사용자가 지웠다"고 보고 반대편도 지웠습니다.
  - 대량 삭제 정지 기준이 짝 수의 20%(약 159개)여서, 103개는 확인 없이 통과했습니다.
- **한쪽이 먼저 사라진 이유(유력):** 브리지가 만든 사본을 동기화 어댑터가 받지 않았거나(Google이 거부한 반복 규칙 등) 새 행으로 바꿔 저장했습니다. 어느 쪽이 먼저였는지는 기록이 없어 확정할 수 없습니다. 0.8.3부터 맞춤 기록을 남깁니다.
- **재발 방지:**
  1. **자동 삭제 없음:** 한쪽에서 사라진 일정은 "한쪽에서만 사라진 일정 n개" 카드에 제목과 함께 보여 주고 기다립니다. 고를 수 있는 것은 두 가지입니다.
     - "되살리기"(권장): 짝 기록을 버리고, 남은 쪽에서 다시 복제합니다.
     - "양쪽에서 지우기": 사용자가 확인한 경우에만 지웁니다.
  2. **서버 도착 확인:** 짝의 각 쪽이 서버 id(`_SYNC_ID`)를 받은 적이 있는지 기록합니다(`samsungConfirmed`/`googleConfirmed`). 서버에 도착한 적 없이 사라진 사본은 삭제가 아니라 "거부·교체"로 봅니다. 그때는 짝만 다시 짓고, 원본은 절대 지우지 않습니다.
  3. **거부된 일정 표시:** 구글이 받지 않은 일정은 한 번만 다시 보내고, 그 뒤로는 내용이 바뀌기 전까지 보내지 않습니다(`bridge.refused`).
  4. **구글로 보내지 않는 일정:** 음력, 제조사 확장(`X-`, `RSCALE`, `LUNAR`) 반복 규칙을 가진 일정은 구글로 복제하지 않고 Samsung에만 둡니다.
  5. **되살리기:** 휴대폰에 아직 남아 있는 삭제 기록(DELETED=1, 동기화 어댑터가 아직 비우지 않은 행)에서 지워진 일정을 찾아 Samsung Calendar로 되살립니다. 연결 화면의 "되살릴 수 있는 지워진 일정 n개" 카드입니다.
  6. **맞춤 기록:** 맞출 때마다 구글로·삼성으로·삭제·삭제 대기·동기화 전 사라짐·구글 불가 개수와 지운 일정 제목을 남깁니다(최근 40건). 연결 화면의 "최근 기록 보기"입니다.
- **휴대폰에서 찾지 못한 일정을 되살리는 곳:**
  - 구글 캘린더 웹 → 설정 → 휴지통(30일)
  - 삼성 캘린더 앱의 휴지통(제공되는 경우)

## 9. 0.8.4: 연결 후 서랍 정리
- **메인 캘린더 카드:** Samsung Calendar ⇄ 구글 메인 계정을 한 줄로 보여 줍니다.
  - 표시: "● 연결됨 · 일정 n · 맞춤 n분 전". 문제가 있으면 빨간 "확인 필요"로 바뀝니다(메인 계정의 동기화 꺼짐·허용 필요, 삭제 대기).
  - 체크박스 하나로 둘을 함께 켜고 끕니다.
  - 줄을 누르면 연결 화면이 열립니다.
  - 구글 메인 계정의 나머지 캘린더(예: 가족)는 카드 아래에 붙습니다.
- **트리에서 뺀 것:** 메인 쌍과 메인 계정 캘린더는 트리에서 빠집니다. 나머지 개인 캘린더(hazakuqa·kgcaudit02·My calendar)는 "다른 캘린더" 묶음으로 처음에 접혀 있습니다.
- **☰ 빨간 점:** 메인 연결에 문제가 있을 때만 켭니다. 쓰지 않는 계정의 "확인 필요"로는 켜지 않습니다.

## 10. 0.8.5: 되살린 일정의 중복 (현정탄신일 두 개)
- **증상:** Samsung Calendar 안에 같은 일정이 두 개 있었습니다. 하나는 원래 색(클레이), 하나는 캘린더 기본색(파랑)입니다.
- **원인:**
  - 사라진 일정이 두 경로로 각각 되살아났습니다(삼성 휴지통 복원 + OLO 되살리기로 추정).
  - OLO 사본은 일정별 색을 옮기지 않았고, 삭제 기록에서 되살린 사본은 알림까지 비어 있었습니다.
  - 그래서 지문이 달라 "완전히 같은 일정"만 찾는 중복 정리에 걸리지 않았습니다.
- **수정:**
  1. 중복 판정을 "제목·시작·끝·반복 규칙이 같음"(`twinKey`)으로 넓혔습니다. 알림·메모·색이 달라도 같은 일정으로 봅니다.
  2. 그중 알림·메모·장소가 가장 많이 남은 쪽을 남깁니다. 같으면 짝 있는 쪽, 그다음 오래된 쪽을 남깁니다.
  3. 중복 정리 카드에 지울 일정 제목을 보여 줍니다. 메인 카드에도 "중복 n개"(빨강)와 ☰ 빨간 점을 표시합니다.
  4. 되살리기는 같은 모양의 일정이 이미 살아 있으면 건너뜁니다. 다른 경로로 이미 되살린 일정을 또 만들지 않기 위해서입니다.
  5. 복사할 때 일정별 색(`EVENT_COLOR`)도 옮겨, 사본이 원본과 같은 색으로 보입니다.

## §17 계정별 지금 동기화 제외 (0.10.0)

- **발견한 문제:** "지금 동기화"는 SYNC_EXTRAS_MANUAL로 요청했다. 수동 요청은 계정 동기화 설정을 무시하므로(SyncRequest.Builder.setManual ≈ setIgnoreSettings), 휴대폰에서 동기화를 꺼 둔 계정까지 동기화되고 있었다.
- **두 단계로 나눴다:**
  - **① 휴대폰 동기화 끄기:** `setSyncAutomatically(false)`로 끈다. 기기 전체와 모든 앱에 적용된다. 계정 칩 메뉴에 "휴대폰 동기화 끄기"를 추가했고 되돌리기를 지원한다.
  - **② 지금 동기화에서 제외:** OLO만 해당한다. `AppSettings.syncExcluded`에 "type/name" 키로 저장한다. Samsung 계정과 Google 계정은 이름(sutest@gmail.com)이 같을 수 있어서 계정 종류까지 붙였다.
- **요청 대상(`syncTargets`):** 동기화 계정 중 제외 목록에 있는 계정과 `getSyncAutomatically == false`인 계정을 뺀다. OLO가 볼 수 없는 "확인 필요" 계정도 여기서 false로 읽혀 빠진다. 지금 동기화가 기다리는 대상(`syncActive`)도 같은 기준을 쓴다.
- **화면:**
  - 동기화 중인 계정 칩을 누르면 메뉴가 열린다: 제외 / 휴대폰 동기화 끄기 / 계정 설정.
  - 제외한 계정은 회색 "제외됨" 칩으로 바뀌고, 같은 메뉴에서 다시 포함할 수 있다.
  - 휴대폰에서 꺼짐이 제외보다 우선해서 표시된다.
- **구글 메인 계정을 제외할 때:** 막지는 않는다. 대신 "아이폰 반영이 늦어질 수 있음"을 붉게 경고한다. 브리지는 15분마다 자동으로 맞추기를 계속한다.
- **서랍 줄:** "n개 계정 제외"를 붙인다. 제외한 계정은 "확인 필요" 경고 수에서 뺀다.
- **설정 → 동기화 → 지금 동기화 대상:** 계정별 체크 목록이다. 휴대폰에서 꺼진 계정은 흐리게 보이고 "자동으로 제외"로 표시된다.
- **보기와는 별개다:** 제외해도 그 계정의 일정은 화면에 그대로 보인다.

### §17-1 계정 단위라는 점을 화면에 맞춤 (0.10.1)

- **동기화 단위:** Android 동기화(requestSync, 자동 동기화 스위치)는 **계정 단위**다. 캘린더 하나만 지금 동기화에서 빼는 수동 요청은 없다. 그래서 Google 묶음의 sutest 카드에서 "제외"를 고르면 sutest 계정 전체가 제외된다. 연동 캘린더에 있는 구글 메인 캘린더와 가족도 함께 빠진다. 다만 같은 이름의 삼성 계정은 키가 달라서 그대로 남는다.
- **화면에서 어긋났던 점과 수정:**
  - Google 묶음의 sutest 카드는 연동으로 옮겨진 캘린더를 뺀 나머지 2개만 보여서, 그 2개에만 적용되는 것처럼 읽혔다. 카드 부제를 "구글 메인 · 연동 외 n개"로 바꿨다.
  - 메뉴 설명을 "계정 전체 n개 캘린더 · 연동 캘린더 포함"으로 바꿔 적용 범위를 분명히 했다.
  - 구글 메인을 제외하면 연동 캘린더 카드에도 "구글 메인 지금 동기화 제외"를 표시한다.
  - 서랍 지금 동기화 줄의 "n개 계정 제외"와 "n개 계정은 확인 필요"는 마지막 실행 때 값을 보여 주고 있었다. 이제 현재 설정에서 바로 계산한다. 그래서 실행한 뒤 계정을 제외해도 경고가 바로 갱신된다.

## §18 자동 삭제 반영과 백그라운드 실행 (0.10.2)

**삭제 자동 반영**
- 확인을 마친 쌍에서 한쪽만 사라진 경우, 한 번의 맞춤에 3개 이하(`AUTO_DELETE_LIMIT`)면 다른 쪽에서도 지운다. 양방향 모두 적용된다(Samsung에서 지우면 구글, 아이폰에서 지우면 Samsung).
- 4개 이상이 한꺼번에 사라지면 0.8.3 사고와 같은 모양으로 보고, 지금처럼 "한쪽에서만 사라진 일정"으로 모아 확인을 기다린다.
- 동기화 전에 사라진 사본(orphan)은 여전히 상대 쪽을 지우지 않는다.
- **되돌리기:** 자동으로 지우기 직전에 일정 내용(BridgeFields)을 `bridge.autoDeleted`에 저장한다. 휴대폰이 삭제 기록(DELETED 행)을 지워도 되돌릴 수 있게 하려는 것이다. 브리지 시트의 "함께 지운 일정 n개" 카드에서 24시간 동안 되돌릴 수 있다. 되돌리면 Samsung Calendar에 다시 만들고(`bridgeCreate`), 맞춤이 구글로 복제한다. 바뀐 반복 회차는 원래 시간으로 돌아오고, 취소된 회차는 제외일로 복원된다.

**백그라운드 실행**
- 브리지를 연결할 때 배터리 최적화 예외(REQUEST_IGNORE_BATTERY_OPTIMIZATIONS)를 한 번 요청한다.
- 앱을 열었을 때 마지막 맞춤이 30분보다 오래됐으면, 닫아 둔 동안 백그라운드 작업이 돌지 않은 것으로 본다(대개 Samsung 절전 관리). 이때 시트에 "자동 맞춤이 n시간 멈춰 있었습니다" 카드를 띄우고, 누르면 절전 예외 요청으로 간다. 이미 예외라면 '잠자는 앱'을 확인하도록 앱 설정 화면을 연다. 연동 카드의 상태 줄에도 같은 내용을 표시한다.
- 맞춤이 실패하면 지난번 보고는 그대로 둔다. 그래서 전에는 실패가 화면에 드러나지 않았다. 이제 "맞춤 실패"와 오류 내용, "다시 맞추기"를 보여 준다.

### §18-1 앱에서 고친 내용이 반영되지 않음 (0.10.3)

- **증상:** OLO에서 일정 종료 시각을 바꿔 저장해도 목록에는 예전 시각이 남았다(현정 사촌남동생 결혼, 12:30 → 1:30). 같은 무렵 짝 수가 794개에서 793개로 줄었다.
- **원인 후보와 조치:**
  1. **조용한 실패:** 저장할 때 provider의 update 결과(수정된 행 수)를 보지 않았다. 이제 0행이면 오류를 낸다. 또 저장 직후 다시 읽어서 제목·시작·종료·장소가 실제로 바뀌었는지 확인하고, 안 바뀌었으면 "일부 항목을 바꾸지 않았습니다"를 띄운다.
  2. **DURATION 잔존:** 브리지가 일정을 제자리에서 고칠 때(plain update) DTEND만 쓰고, 상대 행에 남은 DURATION은 그대로 두었다. Samsung이 만든 행에는 DURATION이 들어 있는 경우가 있다. 이제 DURATION을 지우고, update가 거부되면 실패로 처리해서 다음 맞춤 때 다시 시도한다.
  3. **진단용 기록:** 맞춤 기록에 "구글로 고침: …"과 "삼성으로 고침: …"을 제목과 함께 남긴다. 수정이 반대쪽에서 다시 덮였다면 기록에 바로 드러난다.

### §18-2 종료 시각이 반영되지 않던 진짜 원인 (0.10.4)

- **관찰:** 편집 화면은 저장된 종료 시각(DTEND 15:30)을 읽는데, 상세 화면과 달력은 회차 표(Instances)를 읽어서 12:30을 보였다. 오류는 나지 않았다.
- **원인:** Samsung이 만든 일반(반복 없는) 일정에는 DTEND와 함께 DURATION(P3600S, 1시간)이 들어 있다. OLO는 저장할 때 DURATION을 null로 보내는데, Samsung provider는 이를 무시하고 DURATION을 남겨 둔다. 그러면 회차는 "시작 + 1시간"으로 계산되어, 종료를 바꿔도 화면에 반영되지 않는다. Samsung 앱이나 기기 위젯에서도 같은 일이 생길 수 있다.
- **수정 (`alignLength`):**
  - 저장할 때마다 다시 읽어서, DURATION이 남아 있고 DTEND와 맞지 않으면 DURATION을 새 길이로 다시 쓴다. 바뀐 값이 없어도 실행하므로, 이미 어긋난 일정도 다시 저장하면 고쳐진다.
  - 브리지가 일정을 제자리에서 고칠 때도 같은 처리를 한다.
  - 브리지가 양쪽 캘린더를 읽을 때 어긋난 일반 일정을 찾아 한 번씩 고친다.

### §18-3 저장 결과를 화면 기준으로 확인 (0.10.5)

- 0.10.4 이후에도 기전팀 보고(종료를 2:30으로 바꿈)가 OLO와 Samsung 캘린더 앱 양쪽에서 3:00으로 보였다. 동기화 지연이 아니라, 휴대폰 캘린더 저장소가 이 일정을 옛 길이로 계속 그리는 것이다. 저장소가 왜 이렇게 동작하는지는 휴대폰 없이 확정할 수 없었다.
- **원인 추정 대신 결과를 확인한다:** 일반 일정을 저장한 뒤 휴대폰이 실제로 그리는 회차(Instances)의 종료 시각을 읽는다(`instanceEnd`). 새 종료 시각과 다르면, 같은 값으로 일정을 새로 만들고 원래 행을 지운다.
- **브리지 쪽:** 제자리 수정(plain update)을 한 뒤 같은 확인을 하고, 다르면 새 사본으로 바꾼다.
- **영향:** 다시 만든 일정은 id가 바뀐다. 다음 맞춤에서 브리지는 이를 "원래 일정 삭제 1개 + 새 일정 1개"로 보고, 구글 쪽 사본을 지운 뒤 새로 복제한다. 3개 이하라 자동으로 처리되고 24시간 되돌리기에 남는다.
- **회차를 읽지 못하면:** 다시 만들지 않는다.
- **확인(2026-10-19):** 사용자 휴대폰에서 기전팀 보고의 종료 시각 변경이 반영된 것을 확인했다. 결과를 보고 확인한 뒤 일정을 다시 만드는 방식이 이 Samsung 저장소에서 통한다.
